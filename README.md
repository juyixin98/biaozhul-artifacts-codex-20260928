# Entropic Optimal Transport

A small Python, NumPy, SciPy and FastAPI implementation of entropy-regularized
optimal transport on finite discrete distributions.

## Mathematical Contract

For marginals `a` and `b` with equal total mass `M`, cost matrix `C`, and
regularization `epsilon > 0`, the solver minimizes

```text
<P, C> + epsilon * KL(P/M || (a/M)(b/M)^T) * M.
```

For probability marginals this is

```text
<P, C> + epsilon * sum P_ij * log(P_ij / (a_i b_j)).
```

The response returns separately:

- `original_cost`: `<P, C>`
- `entropy_penalty`: the mass-scaled KL term above
- `regularized_cost`: `original_cost + epsilon * entropy_penalty`

Zero-mass rows and columns remain in the returned matrix but are excluded from
the active Sinkhorn subproblem. The all-zero problem returns an all-zero plan
without iteration.

## Numerical Guarantees

- Inputs are checked for finite values, non-negative masses, dimensions, and
  matching total mass.
- Sinkhorn dual variables are updated in log space using
  `scipy.special.logsumexp`.
- Both row and column log-marginals are checked after every sweep.
- The final primal plan is reconstructed row by row with a row-wise maximum
  shift, avoiding global underflow for kernels such as `exp(-1000 / 1e-6)`.
- If the iteration budget expires before both reconstructed marginals are
  satisfied, the plan is returned as best effort only and the HTTP API reports
  category `resource_exhausted` with status 509; it is never called feasible.

## Configuration

No database or external service is required.

- Python: system `python3`
- Default listen host: `127.0.0.1`
- Default listen port: `8000`
- Run logs: `ENTROPIC_OT_LOG_DIR`, default `runs/`

Installed versions used for verification are pinned in
[requirements.txt](requirements.txt). The current environment already had
these packages, so no virtual environment or installation step was needed.

## Run The Service

From this directory:

```bash
python3 -m uvicorn entropic_ot.service:app --host 127.0.0.1 --port 8000
```

Example request:

```bash
curl -sS http://127.0.0.1:8000/solve \
  -H 'content-type: application/json' \
  -d '{
    "a": [0.5, 0.5],
    "b": [0.5, 0.5],
    "cost": [[0.0, 1.0], [1.0, 0.0]],
    "epsilon": 1.0,
    "max_iterations": 100,
    "tolerance": 1e-10
  }'
```

Important response fields are `plan`, `original_cost`, `regularized_cost`,
`entropy_penalty`, `feasible`, `converged`, `stop_reason`, `row_error`,
`column_error`, and `diagnostics`.

An optional `idempotency_key` replays a completed response. Reusing the same
key with a different payload returns category `state_conflict` with status 409.

## Error Categories

- `input_quality`, HTTP 422: invalid model, shape, finite-value, sign, or total
  mass.
- `state_conflict`, HTTP 409: idempotency key conflict or in-flight reuse.
- `resource_exhausted`, HTTP 509: iteration budget expired with an infeasible
  best-effort plan, or memory allocation failed.
- `computation_failed`, HTTP 500: unexpected or non-finite numerical failure.

## Run Evidence

Every `/solve` run writes one JSONL file named by a timestamp and random run ID.
The log contains:

- start event with parameters, shape, and full input
- sampled iteration states with row and column errors, dual bounds, and log
  plan bounds
- finish event with plan, objectives, marginals, and feasibility reason
- failure event with the stable error category and details

The response includes `run_id` and `replay.log_file`, so the exact input and
decision trail can be re-opened from the configured log directory.

## Tests

Run the complete suite with:

```bash
python3 -m pytest -q
```

The tests are not generated by the solver under test. They include:

- a hand-derived two-point solution with concrete entries and objective
- independent SciPy `linprog` LP comparison for small epsilon
- an independent classical probability-domain multiplicative Sinkhorn
  reference
- zero rows, zero columns, and all-zero mass handling
- large cost and tiny epsilon underflow checks
- budget expiry assertions that explicitly require infeasible status
- input, state, resource, and computation failure category checks
- JSONL run evidence and FastAPI contract tests

See [docs/VERIFICATION.md](docs/VERIFICATION.md) for the recorded verification
run.
